# Ядро магазина цифровых товаров

Бэкенд магазина цифровых товаров (ключи, пополнения, подписки, гифт-карты): REST API создания
заказов, вебхук оплаты с гарантией exactly-once, фоновая доставка через двух поставщиков-заглушек
с фолбэком A→B, двойная бухгалтерская книга и автоматическое восстановление зависших заказов.

Три процесса Node.js поверх одной PostgreSQL:

- `apps/api` — REST API, вебхук оплаты, воркер фоновых задач и sweeper восстановления (один процесс);
- `apps/supplier-stub` — управляемая заглушка поставщика, поднимается дважды (A и B);
- `tools/` — CLI-скрипты для сидинга каталога и ручной проверки сценариев приёмки.

Очередь задач — таблица в той же Postgres (без Redis/BullMQ), фоновые процессы живут внутри
`apps/api` через `@nestjs/schedule`. Внешних сервисов, кроме Postgres, нет.

Дополнительно: [`DATA_FLOW.md`](./DATA_FLOW.md) — сквозной путь заказа, [`spec/`](./spec) —
подробная проектная спецификация, [`spec/requirements.md`](./spec/requirements.md) — текст задания.

## 2. Ключевые решения

### 2.1 Данные и деньги

- **Деньги — `BIGINT` в копейках**, каждая денежная колонка с суффиксом `_minor`: точность по построению, суммирование книги без дрейфа. `NUMERIC` приезжает в JS строкой и тянет десятичную библиотеку, `float` неточен в принципе.
- **`amount` вебхука и `price` каталога — рубли, не копейки** (в контракте `amount: 500` для `STEAM-TOPUP-500` с `price: 500`), перевод ровно `amount * 100`. В ответах отдаются оба поля: `amount_minor` (авторитетное) и `amount` (для показа), а расхождение суммы отваливается громко (`rejected_amount`), а не тихо. Валюта — `CHAR(3)` с `CHECK (currency = 'RUB')`: переключатель валют в исходных данных объявлен «только для отображения».
- **Публичный `ext_id` формата `ord_00123`** из последовательности `order_ext_seq`; клиент может задать свой `client_order_id`, и он становится `ext_id` — это даёт идемпотентность создания заказа и позволяет воспроизвести «вебхук пришёл раньше заказа». Клиентский идентификатор не может быть всецифровым (`^ord_(?!\d+$)[A-Za-z0-9_-]{1,40}$`), иначе занятый заранее `ord_00100` подменил бы собой следующий анонимный заказ.
- **Схема живёт в миграциях, сущности TypeORM — только маппинг** (`synchronize: false`): частичные уникальные индексы, `COLLATE "C"`, `fillfactor` и составные `CHECK` в декораторах не выражаются, а именно на них держится exactly-once. 4 миграции, 10 таблиц.
- **Двойная запись двумя таблицами**: `ledger_txns` (шапка, `UNIQUE (idempotency_key)`) и `ledger_entries` (проводки, `UNIQUE (txn_id, entry_seq)`, генерируемая колонка `signed_minor`). Сумма `signed_minor` внутри проводки обязана быть нулём — «журнал всегда сходится» проверяемо.
- **Три счёта и две проводки**: `payment_captured` (Dt `cash` / Kt `customer_prepayment`) и `delivery_recognized` (Dt `customer_prepayment` / Kt `revenue`), сумма всегда `orders.total_minor`. Выручка признаётся в момент выдачи, а не оплаты, иначе непоставленный заказ выглядел бы доходом; вебхук `failed` не пишет ни одной проводки.
- **`postTxn` — единственный писатель книги, проверка до записи** (минимум две записи, целые положительные суммы, одна валюта, `SUM(signed) = 0`); нарушение рвёт объемлющую транзакцию, поэтому несходящаяся проводка физически не попадает в БД. Своей транзакции не открывает — принимает `QueryRunner` вызывающего, чтобы деньги, статус заказа и постановка задачи фиксировались вместе.

### 2.2 Exactly-once

- **Статус заказа меняет одна охраняемая функция и один писатель.** `resolveTransition(from, event)` (`orders/order-state-machine.ts`) — единственное место, где решается допустимость перехода: 7 статусов × 9 событий, четыре исхода (`apply`/`noop`/`conflict`/`illegal`). Пишет статус только `OrdersRepository.transition` через CAS `UPDATE … WHERE id = $1 AND status = $2`: ноль изменённых строк = «нас опередила другая транзакция», обработчик перечитывает строку и заново спрашивает машину, а не затирает чужой результат.
- **Шлюз идемпотентности — вставка события первым шагом транзакции**: `INSERT INTO payment_events … ON CONFLICT (event_id) DO NOTHING RETURNING id`. Ноль строк = событие уже видели, транзакция коммитится немедленно с `result: "duplicate"` — без блокировки заказа, без проводки, без постановки задачи.
- **Блокировка строки заказа** (`SELECT … WHERE ext_id = $1 FOR UPDATE`) — единственная точка сериализации гонки 50 вебхуков. Под READ COMMITTED ожидающая транзакция после снятия блокировки перечитывает последнюю зафиксированную версию строки, поэтому второй запрос видит уже `paid`, получает `noop` и не пишет ни проводки, ни задачи. Внешний мьютекс/Redis-lock не нужен: база даёт то же бесплатно и со снятием при коммите.
- **Четыре независимых уровня защиты от двойной выдачи** — любого одного достаточно:

  | Уровень | Механизм                                                                                    |
  | ------- | ------------------------------------------------------------------------------------------- |
  | 1       | `payment_events_event_uq` — дедуплицирует идентичные события                                |
  | 2       | `SELECT … FOR UPDATE` по заказу — сериализует разные события одного заказа                  |
  | 3       | `jobs_live_uq` — частичный `UNIQUE (kind, dedupe_key) WHERE state IN ('pending','running')` |
  | 4       | `issued_deliveries_order_uq` — вторая выдача физически невозможна                           |

  Плюс `ledger_txns_idem_uq` (ровно две проводки на захват платежа), `delivery_attempts_open_uq` (не более одного живого вызова поставщика), `stock_keys_order_uq` и `issued_deliveries_stock_key_uq` (один ключ — не более одного заказа и одной выдачи).

- **В транзакции вебхука нет ни одного сетевого вызова**: только вставка события, блокировка заказа, переход статуса, проводка и постановка задачи — пять коротких операций по индексированным строкам. Вся доставка (резервация ключа или `POST /issue`, ретраи, бэкофф, фолбэк) идёт асинхронно в воркере. Инлайн-доставка означала бы удержание блокировки строки заказа через сетевой вызов с таймаутом 2 с и до четырёх попыток: ~10-секундный вебхук, гарантированный таймаут у провайдера и шторм повторов поверх гонки.
- **Коды ответа вебхука**: любой бизнес-исход (включая `duplicate`, `orphan`, `conflict`) — `200` (событие принято и durably записано, повтор ничего не изменит); нарушение схемы тела — `400` (повтор не исправит плохой payload); внутренняя ошибка — `500` (провайдер повторит доставку — именно это нужно, если событие не удалось сохранить).

### 2.3 Если вебхук вне порядка

| Ситуация                                                   | Политика и почему                                                                                                                                                                                                                            |
| ---------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Вебхук раньше заказа                                       | Событие сохраняется как `orphan` (`order_id = NULL`), ответ `200`; разгребает проход 6a sweeper'а, `orphan` старше `ORPHAN_TTL_SECONDS` → `abandoned`. `404`/`5xx` заставили бы провайдера слать вебхук вечно и рисковали бы потерей события |
| `failed` после применённого `paid`                         | `conflict`, заказ **не** откатывается: `paid` — факт движения денег, откат требует флоу возврата, который задание исключает. Аномалия становится громкой (ERROR-лог, `state='conflict'`), а не молчаливой                                    |
| `paid` после `payment_failed`                              | `conflict`, заказ остаётся в терминальном `payment_failed`                                                                                                                                                                                   |
| Устаревшее событие (`occurred_at < last_payment_event_at`) | `ignored_stale`: порядок задаёт метка времени провайдера, а не порядок прихода запросов — единственный корректный сигнал при at-least-once доставке                                                                                          |
| Несовпадение суммы/валюты у `paid`                         | `rejected_amount`, без перехода и проводок. Амаунт-гвард проверяется раньше гварда устаревания: приоритет у более информативной причины отказа                                                                                               |
| Неизвестное поле в теле                                    | Молча отбрасывается вместо `400`: провайдер может добавить поле в payload в любой момент, и падать `400` на каждый его релиз значит терять реальные платежи                                                                                  |

Итог — восемь значений `result`: `applied`, `duplicate`, `orphan`, `ignored_stale`, `ignored_already_paid`, `ignored_terminal`, `conflict`, `rejected_amount`.

### 2.4 Очередь задач и интеграция с поставщиками

- **Очередь — таблица `jobs` в той же Postgres.** Постановка задачи (`INSERT … ON CONFLICT DO NOTHING` по частичному уникальному индексу) — часть той же транзакции, что проводка и смена статуса: коммитятся вместе или откатываются вместе. Claim — атомарный `UPDATE … WHERE id IN (SELECT … FOR UPDATE SKIP LOCKED) RETURNING`: два воркера не могут взять одну строку и ни один не блокируется на чужой выборке. С внешним брокером задача ставилась бы вторым, не атомарным с бизнес-транзакцией шагом (либо outbox, либо риск задачи для откатившегося заказа).
- **Claim и settle — раздельные транзакции**: `claim()` коммитится сразу (`state='running'`, `attempts+1` должны быть видны другим воркерам и пережить падение процесса). Одна транзакция на весь жизненный цикл держала бы соединение открытым на время сетевого таймаута поставщика. Бэкофф — свой `jobs/backoff.util.ts` (~20 строк): экспоненциальный рост с равным джиттером, чистая функция от `attempts`, `baseMs`, `maxMs` и инжектируемого `random()`; библиотеки вида `p-retry` делают retry вокруг вызова в процессе, а здесь нужно посчитать `run_at` и записать его в БД до следующего claim'а другим процессом.
- **Таймаут ≠ отказ.** Вызов ограничен `AbortSignal.timeout` (по умолчанию 2000 мс); сработавший таймер даёт исход `unknown` (`error_kind: 'timeout'`), а не `unavailable`: факт таймаута ничего не говорит о том, успел ли поставщик зачеканить код. Считать таймаут отказом и сразу идти на фолбэк значило бы иногда выдавать код дважды. «Определённый» исход двигает выбор поставщика, «неопределённый» требует дозвона (`suppliers/suppliers.util.ts`):

  | Исход сети / HTTP                                             | `kind`                     | `error_kind`            | Определённый? |
  | ------------------------------------------------------------- | -------------------------- | ----------------------- | ------------- |
  | `TimeoutError`/`AbortError` (клиентский таймаут)              | `unknown`                  | `timeout`               | нет           |
  | `ECONNREFUSED`/`ENOTFOUND`/`EAI_AGAIN`/`EACCES` (нет connect) | `unavailable`              | `connection_refused`    | да            |
  | `ECONNRESET`/`EPIPE` (разрыв уже после connect)               | `unknown`                  | `connection_reset`      | нет           |
  | HTTP `2xx` с `code` / без `code`                              | `issued` / `unknown`       | — / `bad_body`          | да / нет      |
  | HTTP `4xx` / `5xx`                                            | `rejected` / `unavailable` | `http_4xx` / `http_5xx` | да            |
  | тело с `reason: 'out_of_stock'` (любой статус)                | `out_of_stock`             | `out_of_stock`          | да            |

  `EACCES` лежит в корзине «отказано в соединении» не по опечатке: ОС отказала в `connect()` до того, как хоть один байт ушёл с машины, — гарантия «поставщик не видел запрос» та же, что у `ECONNREFUSED`. `ECONNRESET` в неё не идёт: разрыв случается после установления соединения, часть запроса могла уйти.

- **Запись попытки в БД строго до сетевого вызова (record-before-call).** Строка `delivery_attempts` (`state='in_flight'`, с уже вычисленным `request_id`) вставляется и коммитится, и только потом — вне транзакции — уходит `POST /issue`. Если процесс упадёт между коммитом и вызовом, следующий claim найдёт эту же строку и переиграет тот же `request_id` вместо того, чтобы завести новую попытку поверх возможно уже выданного кода.
- **`request_id = req_{extId без "ord_"}-g{generation}-{supplierCode}{attemptNo}`** (например `req_00123-g1-A1`): какой заказ, какое поколение доставки, какой поставщик и какая попытка к нему. Составной ключ даёт бесплатную идемпотентность на стороне поставщика — повтор с тем же `request_id` обязан вернуть тот же код; побочное следствие — у A и B физически не может быть общего `request_id`.
- **Разрешение `unknown` — тот же `request_id`, повторный `POST`, ограниченный бюджет дозвонов.** `settleUnknown` переводит попытку в `state='unknown'` с `resolve_attempts+1` и `next_resolve_at`, задача уходит на переклейм, на следующей итерации находится та же строка и запрос повторяется. После `SUPPLIER_UNKNOWN_MAX_RESOLVE_ATTEMPTS` (по умолчанию 5) попытка помечается `abandoned_unknown` и выбор переходит к следующему поставщику: заказ не виснет навечно, но и не считается точно доставленным этим поставщиком.
- **Фолбэк A→B срабатывает только на определённом исходе** (`unavailable`/`rejected`/`out_of_stock`, но не `unknown`). Внутри одного поставщика — до `SUPPLIER_MAX_ATTEMPTS_PER_SUPPLIER` (по умолчанию 2) повторов и только на `http_5xx`: прочие определённые неудачи сразу двигают выбор дальше, повтор к тому же поставщику ничего не изменит.
- **Исчерпание цепочки ведёт в терминальный статус, а не в подвешенный заказ.** Оба поставщика ответили `out_of_stock` → `out_of_stock`; хотя бы один завершился иначе (`http_5xx`-бюджет, `abandoned_unknown`) → `delivery_failed` со сводкой причин (`"A=http_5xx, B=abandoned_unknown"`). Отдельно: если у задачи кончились попытки воркера раньше, чем поставщики отдали терминальный исход, `forceDeliveryFailed` всё равно переводит заказ в `delivery_failed` — иначе он остался бы в `delivering` навсегда.
- **Circuit breaker осознанно не реализован**: поставщиков фиксированно два, каждый вызов ограничен своим таймаутом, весь прогон доставки — `SUPPLIER_JOB_BUDGET_MS` (10 000 мс), а решение «пробовать ли A» принимается заново на каждой попытке по исходам **этого же заказа**, а не по глобальной статистике. Breaker добавил бы разделяемое между воркерами состояние и пороги без видимого выигрыша при двух известных поставщиках.

### 2.5 Наблюдаемость и восстановление

- **JSON-логи собственным `JsonLogger`** (~70 строк, ноль зависимостей): одна JSON-строка на запись со стабильным набором полей (`ts`, `level`, `event`, `ctx`, `trace_id`, `order_id`, `event_id`, `request_id`, `job_id`, `duration_ms`, `data`, `msg`); `msg` дублирует `event`, чтобы `docker logs` читался без `jq`. **Коды выдачи в логах только маскированные** (`A7X1-****-**CD`) — полный код живёт лишь в БД и в ответе `GET /orders/:id`. Требование звучит как «структурированные логи», то есть форма JSON, а не конкретная библиотека.
- **Сквозной `trace_id` через `AsyncLocalStorage`**: middleware берёт `x-request-id` или генерирует `crypto.randomUUID()`, возвращает его в ответном заголовке и открывает контекст, из которого логгер сам достаёт корреляцию — ни один вызов не тащит id параметром. Фоновые задачи открывают контекст с `trace_id` из `jobs.trace_id`, поэтому трасса вебхука доходит до вызова поставщика.
- **Sweeper** (`reconciliation/sweeper.service.ts`) — `@Interval` на `SWEEPER_INTERVAL_MS` (по умолчанию 15 000 мс), отключается через `SWEEPER_ENABLED=false`. Прогон = 6 проходов, каждый в своей короткой транзакции, батчем не больше `SWEEPER_BATCH_SIZE` строк и с `SKIP LOCKED` там, где проход конкурирует с воркером или другим тиком:

  | Проход | Что делает                                                                                                            |
  | ------ | --------------------------------------------------------------------------------------------------------------------- |
  | 1      | реклейм задач, зависших в `running` дольше `JOB_LOCK_TTL_MS`                                                          |
  | 2      | `paid`/`delivering` дольше `STUCK_ORDER_AGE_SECONDS` без выдачи и без живой задачи — ставит доставку в очередь заново |
  | 3      | `out_of_stock` с пополненным остатком — немедленный повтор, без порога давности                                       |
  | 4      | `delivery_failed` старше `DELIVERY_FAILED_RETRY_SECONDS`, под потолком `MAX_DELIVERY_GENERATIONS`                     |
  | 5      | 5a: `in_flight` дольше `ATTEMPT_INFLIGHT_TIMEOUT_MS` демотится в `unknown`; 5b: готовые `unknown` редрайвятся         |
  | 6      | 6a: orphan-событие, для которого заказ уже появился, реплеится; 6b: orphan старше TTL → `abandoned`                   |

  Проход 4 увеличивает `delivery_generation`: без инкремента старая и новая задачи доставки не различались бы по поколению, и проверка «пропусти устаревшую задачу» ломалась бы именно на пути восстановления. Проход 5b редрайвит `unknown` через ту же задачу `deliver_order`, а не через отдельный обработчик — повторный `/issue` с тем же `request_id` идемпотентен.

- **Ручной путь восстановления поверх тех же инвариантов** — `POST /admin/orders/:id/redeliver`: сначала проверяет `issued_deliveries` (уже есть выдача → `409`, даже если статус заказа этого не отражает), затем восстановимость статуса, затем бампает `delivery_generation` и ставит задачу — форсирует то, что проход 3/4 сделал бы сам по расписанию. `POST /admin/products/:sku/restock` пополняет остаток и **после коммита** уведомляет стенд поставщика; вызов обёрнут в try/catch и только логирует ошибку — ресток в своей БД не должен откатываться из-за недоступной заглушки.
- **`POST /orders` не разгребает orphan-события** при создании заказа: единственный путь — проход 6a sweeper'а. Сознательное упрощение: не дублировать логику реплея ради разницы в задержке на один тик.

### 2.6 Модель остатков и каталог

- **Два режима выдачи, один конвейер.** `products.fulfillment_mode`: `pool` — коды из собственной таблицы `stock_keys`; `supplier` — код чеканит поставщик A с фолбэком на B. Соответствие закреплено структурно: `CHECK ((type = 'key') = (fulfillment_mode = 'pool'))`. «Всё через поставщиков» обесценило бы пул ключей, «всё из пула» сделало бы ловушку таймаута ненастоящей.
- **«Один ключ не может уйти в два заказа» гарантирует база, а не код**: атомарная резервация `UPDATE stock_keys … WHERE id = (SELECT id … FOR UPDATE SKIP LOCKED LIMIT 1)` плюс три уникальных индекса (`stock_keys_order_uq`, `issued_deliveries_stock_key_uq`, `issued_deliveries_order_uq`).
- **Счётчик остатка вынесен в отдельную таблицу `sku_stock`** (`fillfactor = 70`), а на `products` (`fillfactor = 90`) остался булев `in_stock` — предикат витрины: часто пишущийся счётчик прямо в `products` инвалидировал бы горячие страницы каталога на каждой выдаче. Для режима `supplier` `available_count` — наша локальная оценка доступности поставщика, засеваемая `SUPPLIER_VIRTUAL_STOCK`: уменьшается на успешной выдаче, обнуляется, когда оба поставщика ответили `out_of_stock`, восстанавливается admin-эндпоинтом (спрашивать остаток у поставщика на каждый показ витрины — сетевой вызов в горячем пути ради числа, которое всё равно устареет к моменту оплаты).
- **Витрина спроектирована под keyset-пагинацию**: `products.sku` объявлен `COLLATE "C"` (сравнение по байтам, стабильный порядок независимо от локали БД), запрос сортирует по `(sku, id)` и берёт `limit + 1` строку, чтобы вернуть `has_more` без `COUNT(*)`. Само поле курсора в публичном API не выведено (`next_cursor` всегда `null`) — это часть этапа 5, см. §2.7.
- **Сидер идемпотентен**: товары обновляются `ON CONFLICT (sku)`, ключи вставляются `ON CONFLICT DO NOTHING`, `available_count` для пула пересчитывается из фактически свободных ключей, поэтому уже выданный ключ никогда не «воскресает».

### 2.7 Что осталось за рамками (осознанно)

- **HTTP-отчёт сверки** «оплачен, но не выдан» / «выдан, но не оплачен» (`GET /reconciliation/*`) **не реализован**. Из этапа 4 сделано остальное: структурированные логи по платежам и выдаче, всегда сходящийся журнал денежных движений и фоновая задача, безопасно доводящая зависшие заказы. Расхождения сейчас устраняются автоматически (проходы 2/3/4/6) и видны в БД и логах, но отдельного отчёта для оператора нет; индексы под него в схеме заложены (`idx_orders_paid_undelivered`, `idx_orders_recoverable`).
- **Этап 5 (каталог под нагрузкой) не реализован**: нет генератора тысяч SKU, замеров и разбора `EXPLAIN ANALYZE`, нет курсора в публичном API каталога. Схемная часть частично сделана (§2.6), но без замеров утверждать «запрос остаётся быстрым на тысячах SKU» было бы необоснованно. Скрипты `npm run seed:bench` и `npm run bench:explain` объявлены в `package.json`, но кода за ними нет.
- **Остальные admin-эндпоинты** из исходного плана (`force-paid`, `refund`, `jobs/drain`, `reconcile/stock`) не реализованы: событие `ADMIN_FORCE_PAID` и тип проводки `payment_refunded` объявлены в машине состояний и плане счетов, но кода за ними нет — работают только три эндпоинта из §5.5.
- **Проверка подписи вебхука** — задание прямо снимает это требование, а без описанного механизма любая имитация была бы произвольной.
- **Многопозиционные заказы**: один SKU и `quantity = 1`, закреплено `CHECK (quantity = 1)` — задание описывает выдачу одного кода на заказ. **Полнотекстовый/нечёткий поиск по каталогу**: `GET /catalog?q=` делает префиксный `LIKE` с экранированием метасимволов, без `pg_trgm` — полноценный поиск относится к этапу 5.

### 2.8 Масштабирование

- **`apps/api` масштабируется горизонтально уже сейчас**: в процессе не хранится состояние, вся координация идёт через Postgres (`FOR UPDATE SKIP LOCKED` для очереди и резервации ключей, уникальные индексы вместо блокировок в памяти). Несколько реплик за балансировщиком безопасно делят одну очередь и один пул ключей без изменений в коде; тест критерия 1 фактически проверяет этот сценарий на 50 параллельных запросах.
- **Узкое место — одна БД**: до шардирования масштабирование вертикальное плюс read-реплика для `GET /catalog` (частый, редко меняющийся запрос) с записью по-прежнему на primary. Очередь на таблице `jobs` масштабируется ростом числа воркеров тем же `SKIP LOCKED`; предел — конкуренция за строки `jobs` при очень большом числе воркеров, для единиц-десятков это не проблема, при кратно большей нагрузке следующий шаг — вынести очередь в BullMQ/Redis.
- **Каталог под нагрузкой**: схема заложена (§2.6), замеров нет (§2.7). Первое, что нужно при росте до тысяч SKU — вывести курсор keyset-пагинации в публичный API и снять `EXPLAIN ANALYZE` на реальном объёме. **Circuit breaker** — первое, что стоит пересмотреть при росте числа внешних поставщиков (§2.4).

Нужны Docker (с `docker compose`) и Node.js ≥ 22.12 на хосте (Node — только для CLI-скриптов
`tools/`: сидинг каталога, воспроизведение гонки и фолбэка).

### 3.1 Скрипты `start` (рекомендуется)

```powershell
.\start.ps1 -Seed    # Windows / PowerShell
```

```bash
chmod +x start.sh && ./start.sh --seed    # Linux / macOS
```

Скрипт создаёт `.env` из `.env.example` (если его нет), поднимает `docker compose up -d`, ждёт

каталог (сидер запускается на хосте, поэтому нужен `npm ci` в корне). Без флага база остаётся
пустой: схема есть, товаров нет.

### 3.2 Через docker compose вручную

```bash
cp .env.example .env
docker compose up -d
npm ci                  # зависимости на хосте для CLI-скриптов tools/
npm run seed:catalog    # 12 SKU + 50 ключей в пул

curl -i http://localhost:3000/health        # проверка, что стенд поднялся
curl -i http://localhost:3000/health/ready
curl -s http://localhost:3000/catalog
```

**Миграции применяются автоматически** внутри контейнера `api` при старте
(`apps/api/docker-entrypoint.sh`), отдельный `npm run migration:run` не нужен. Полный сброс —
`docker compose down -v` (снести том с данными), затем заново.

### 3.3 Что кладёт сидер

`npm run seed:catalog` (идемпотентен) заполняет каталог из
[`stock/products.json`](./stock/products.json) и [`stock/keys.json`](./stock/keys.json):
**12 SKU** — 3 типа `key` (`KEY-CS2-PRIME`, `KEY-GTA5`, `KEY-EFT`) с выдачей из собственного пула и
9 остальных (`STEAM-TOPUP-*`, `SUB-*`, `GIFT-*`) с выдачей через поставщиков A/B; **50 ключей** в
пул с раскладкой 20/20/10 по трём `key`-SKU; для SKU режима `supplier` — виртуальный остаток
`SUPPLIER_VIRTUAL_STOCK` (по умолчанию 1000).

## 4. Карта сервисов, портов и переменных

| Сервис                           | Порт   | Роль                                                                       |
| -------------------------------- | ------ | -------------------------------------------------------------------------- |
| `apps/api`                       | `3000` | REST API, вебхук оплаты, воркер фоновых задач и sweeper (в одном процессе) |
| `apps/supplier-stub` (инстанс A) | `4001` | Заглушка поставщика A: `/issue`, `GET /issue/:request_id`, `/_control/*`   |
| `apps/supplier-stub` (инстанс B) | `4002` | Заглушка поставщика B: тот же образ, другие `SUPPLIER_ID` и порт           |
| `postgres`                       | `5432` | Единственный источник истины: данные, очередь задач, бухгалтерская книга   |

Воркер задач и sweeper — не отдельные процессы и не отдельные порты, а `@nestjs/schedule`-таски
внутри `apps/api`, отключаемые через `WORKER_ENABLED=false` / `SWEEPER_ENABLED=false`. `api` и оба
стенда ждут health-чек `postgres` (`pg_isready`) перед стартом.

Полный список переменных с комментариями — в [`.env.example`](./.env.example). Обязательна ровно
одна: `DATABASE_URL`; при отсутствии или неверном значении любой переменной процесс не стартует и
печатает одним сообщением весь список проблем. Самые важные:

| Переменная                                              | Сервис               | Назначение                                                     |
| ------------------------------------------------------- | -------------------- | -------------------------------------------------------------- |
| `DATABASE_URL`                                          | `apps/api`, `tools`  | строка подключения к PostgreSQL (обязательна)                  |
| `PORT`                                                  | все                  | HTTP-порт (`3000` / `4001` / `4002`)                           |
| `SUPPLIER_A_BASE_URL`, `SUPPLIER_B_BASE_URL`            | `apps/api`, `tools`  | базовые URL заглушек поставщиков                               |
| `SUPPLIER_REQUEST_TIMEOUT_MS`                           | `apps/api`           | таймаут одного вызова к поставщику (по умолчанию `2000`)       |
| `WORKER_ENABLED`, `SWEEPER_ENABLED`                     | `apps/api`           | включение воркера задач и sweeper'а восстановления             |
| `ADMIN_API_ENABLED`, `ADMIN_TOKEN`                      | `apps/api`           | доступность `/admin/*` и значение заголовка `x-admin-token`    |
| `SUPPLIER_ID`                                           | `apps/supplier-stub` | идентификатор стенда: `A` / `B`                                |
| `STUB_FAIL_RATE`, `STUB_TIMEOUT_RATE`, `STUB_SLOW_RATE` | `apps/supplier-stub` | доли отказов / зависаний / медленных ответов в режиме `normal` |
| `API_BASE_URL`                                          | `tools`              | базовый URL API для CLI-скриптов                               |

В `docker compose` заглушки поднимаются с ненулевым хаосом (A: 20 % ошибок / 20 % зависаний / 30 %
медленных ответов; B: 10 % / 5 % / 20 %) — это боевой режим для ручных проверок. Интеграционные
тесты принудительно ставят все три ставки в `0` и включают хаос точечно через `/_control/scenario`.

## 5. API

Единый конверт ошибки: `{"error":{"code","message","details","trace_id"}}`. Коды:
`VALIDATION_FAILED` (400), `UNAUTHORIZED` (401), `ADMIN_DISABLED` (403),
`PRODUCT_NOT_FOUND`/`ORDER_NOT_FOUND` (404), `PRODUCT_INACTIVE`/`ILLEGAL_TRANSITION`/
`ORDER_ALREADY_DELIVERED`/`ORDER_NOT_RECOVERABLE` (409), `INTERNAL_ERROR` (500). Валидация строгая
(`whitelist`, `forbidNonWhitelisted`) — кроме тела вебхука оплаты (§2.3). Свой `x-request-id`
подхватывается, возвращается в ответном заголовке и попадает в `trace_id` всех лог-строк запроса.

### 5.1 Health

| Метод и путь        | Назначение                           | Ответ                                          |
| ------------------- | ------------------------------------ | ---------------------------------------------- |
| `GET /health`       | liveness                             | `200` `{ status, service, version, uptime_s }` |
| `GET /health/ready` | readiness (проверка соединения с БД) | `200` / `503` `{ status, ...components }`      |

### 5.2 Каталог

**`GET /catalog`** — витрина остатков. Query: `type` (`key`\|`topup`\|`subscription`\|`giftcard`),
`in_stock` (по умолчанию только товары в наличии), `limit` (1…`CATALOG_MAX_LIMIT`, по умолчанию 24),
`q` (префикс SKU).

```jsonc
// 200 — next_cursor всегда null: курсор keyset-пагинации не выведен в API, см. §2.7
{
  "items": [
    {
      "sku": "KEY-GTA5",
      "name": "GTA V ключ активации",
      "type": "key",
      "amount_minor": 199000,
      "amount": 1990,
      "currency": "RUB",
      "image": "assets/gta5.png",
      "available_count": 20,
      "in_stock": true,
    },
  ],
  "next_cursor": null,
  "has_more": false,
  "limit": 24,
}
```

**`GET /catalog/:sku`** — карточка товара: `200` с тем же объектом, что элемент `items`;
`404 PRODUCT_NOT_FOUND`, если SKU нет или товар деактивирован.

### 5.3 Заказы

**`POST /orders`** — создать заказ. Идемпотентен по `client_order_id`: повтор возвращает `200` и тот
же заказ, ничего не меняя. Наличие товара при создании **не проверяется** — оно проверяется при
доставке, иначе критерий 6 («пустой остаток, восстановимое состояние») был бы непроверяем.
Ошибки: `404 PRODUCT_NOT_FOUND`, `409 PRODUCT_INACTIVE`.

```jsonc
// запрос
{
  "sku": "STEAM-TOPUP-500",      // обязательно
  "client_order_id": "ord_my-1", // опционально, становится order_id; не может быть всецифровым
  "quantity": 1,                 // опционально, допустимо только 1
  "buyer_email": "a@b.c"         // опционально
}
// ответ: 201 — новый заказ, 200 — повтор по client_order_id
{
  "order_id": "ord_00100", "status": "created", "sku": "STEAM-TOPUP-500", "quantity": 1,
  "amount_minor": 50000, "amount": 500, "currency": "RUB", "created_at": "2026-09-04T12:00:00.000Z"
}
```

**`GET /orders/:orderId`** — карточка заказа с историей: до 20 последних платёжных событий и все
попытки доставки. `404 ORDER_NOT_FOUND` для неизвестного заказа. `delivery.code` — единственное
место, где полный код выдачи покидает БД: в логах он маскирован.

```jsonc
// 200
{

      "event_id": "evt_1",
      "status": "paid",
      "state": "applied",
      "occurred_at": "…",
      "received_at": "…",
```

### 5.4 Вебхук оплаты

**`POST /webhooks/payment`** — приём события платёжного провайдера. Всегда `200` на любой
бизнес-исход (§2.2), `400` на нарушение схемы тела, `500` если событие не удалось сохранить.
Неизвестные поля в теле молча отбрасываются. Значения `result` и их условия — §2.3.

```jsonc
// запрос — контракт из задания
{
  "event_id": "evt_a1b2c3",  // уникален для события; повтор приходит с тем же
  "order_id": "ord_00100",
  "status": "paid",          // paid | failed
  "amount": 500,             // в рублях (major units), не в копейках
  "currency": "RUB",
  "created_at": "2026-09-04T12:00:00Z"
}
// ответ: 200
{
  "accepted": true,
  "result": "applied",    // applied|duplicate|orphan|ignored_stale|ignored_already_paid|ignored_terminal|conflict|rejected_amount
  "order_status": "paid", // null, если заказа ещё нет (orphan)
  "event_id": "evt_a1b2c3"
}
```

### 5.5 Admin

Все `/admin/*` требуют заголовок `x-admin-token`, сверяемый с `ADMIN_TOKEN` константным по времени
сравнением. `ADMIN_API_ENABLED=false` отключает весь `/admin/*` целиком (`403 ADMIN_DISABLED`
независимо от токена). Пустой `ADMIN_TOKEN=` снимает саму проверку токена — удобно для локальной
отладки, недопустимо в проде.

**`POST /admin/sweeper/run`** — форсировать один внеочередной прогон всех 6 проходов sweeper'а
(§2.5). Тело не нужно. Ответ `200` — счётчик тронутых строк по каждому проходу:

```jsonc
{
  "reclaimed_stale_jobs": 0,
  "requeued_stuck_orders": 1,
  "retried_out_of_stock": 0,
  "retried_delivery_failed": 0,
  "demoted_stale_inflight": 0,
  "redriven_unknown_attempts": 0,
  "replayed_orphans": 2,
  "abandoned_orphans": 0,
}
```

**`POST /admin/products/:sku/restock`** — пополнить остаток SKU. Ровно одно из двух полей:
`{"codes":["AAAA-BBBB-CCCC","DDDD-EEEE-FFFF"]}` — явный список (только для
`fulfillment_mode=pool`), либо `{"count":10}` — количество (`pool` — сгенерировать коды,
`supplier` — долить виртуальный остаток). Ответ `200` `{ "added": 10, "available_count": 30 }`.
`400 VALIDATION_FAILED` — оба поля или ни одного, либо `codes` для SKU режима `supplier` (у него нет
собственных кодов в БД); `404 PRODUCT_NOT_FOUND` — нет такого SKU.

**`POST /admin/orders/:orderId/redeliver`** — форсировать повторную доставку заказа в статусе
`out_of_stock`/`delivery_failed`. Тело опционально: `{ "reason": "manual retry after restock" }`.
Ответ `202` `{ "enqueued": true, "generation": 2 }`. Ошибки: `409 ORDER_ALREADY_DELIVERED` (выдача
уже есть), `409 ORDER_NOT_RECOVERABLE` (статус не восстановим), `404 ORDER_NOT_FOUND`.

### 5.6 Заглушка поставщика

| Метод и путь              | Назначение                                                                                                                                                   |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `POST /issue`             | выдать код по контракту задания: `{ request_id, sku, order_id }` → `{ status, request_id, code }`; повтор с известным `request_id` возвращает **тот же** код |
| `GET /issue/:requestId`   | посмотреть ранее выданный код (для ручной инспекции; `apps/api` этот канал не использует)                                                                    |
| `GET /inventory`          | остаток стенда                                                                                                                                               |
| `GET /health`             | liveness                                                                                                                                                     |

## 6. Проверка критериев приёмки

Команды ниже — против поднятого `docker compose`-стенда с засеянным каталогом (§3). Каждый критерий
покрыт и автоматическим тестом (§7), и ручным CLI-прогоном.

### 6.1 Гонка: 50 параллельных вебхуков (критерии 1 и 2)

**Автоматически** — основная проверка: `apps/api/test/integration/webhook-race.worker.spec.ts`
поднимает API и оба стенда на тестовых портах, создаёт заказ, шлёт 50 параллельных
`POST /webhooks/payment` с **разными** `event_id` на один заказ (время события — с детерминированным
джиттером, без `Math.random()`), затем проверяет ровно одну проводку захвата платежа, ровно одну
задачу доставки, ровно одну выдачу и сходимость книги. 5 итераций для каждого из двух режимов выдачи.

```bash
npm run test:integration -- webhook-race
```

**Вручную** — `npm run race`: создаёт (или использует существующий) заказ, переводит стенд A в
предсказуемый сценарий `ok` на время прогона (восстанавливая `normal` после), шлёт N параллельных
вебхуков с разными `event_id` на один заказ и печатает таблицу PASS/FAIL из 16 проверок.

```bash
npm run race -- --sku KEY-GTA5 --count 50          # режим pool
npm run race -- --sku STEAM-TOPUP-500 --count 50   # режим supplier
npm run race -- --order ord_00123 --count 50       # против существующего заказа
```

| Группа                              | Что проверяется                                                                                                                                                                                                                                                                   |
| ----------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| HTTP-ответы (4)                     | все ответы `200`; ровно один `result: applied`; ноль `duplicate`/`conflict`/`rejected_amount`/`orphan`; остальные — только `ignored_already_paid`/`ignored_stale`                                                                                                                 |
| Доставка (3)                        | `GET /orders/:id` отвечает; заказ дошёл до терминального статуса; в ответе есть `delivery.code`                                                                                                                                                                                   |
| SQL (9, пропускаются при `--no-db`) | ровно `--count` строк в `payment_events` и ровно одна `applied`; ровно одна задача `deliver_order` в состоянии `done`; ровно одна строка в `issued_deliveries`; 2 проводки и 4 записи в книге; `sum(signed_minor) = 0`; ровно один дебет `cash`; согласованность источника выдачи |

Ненулевой код выхода (хотя бы один `FAIL`) означает регресс инварианта exactly-once и считается
провалом прогона ровно как провал теста. Флаги: `--no-db`, `--no-stub-control`, `--reset-stubs`,
`--api`, `--timeout-ms`; справка — `npm run race -- --help`.

Точечная проверка одного исхода вебхука (`duplicate`, `orphan`, `rejected_amount`, …) —
`npm run webhook -- --order ord_00123 --status paid --amount 500`.

### 6.2 Отказ поставщика и фолбэк A→B (критерий 5)

**Одной командой** — `npm run demo:fallback -- --fail-mode stopped`: скрипт выставляет стендам
сценарии (B — всегда `ok`, A — по `--fail-mode`), создаёт и оплачивает заказ на SKU режима
`supplier`, дожидается терминального статуса и печатает таблицу PASS/FAIL из 11 проверок (режим SKU,
оплата, выдача именно от B, состав `delivery_attempts`, счётчики выдачи заглушек), восстанавливая
сценарии в `normal` по завершении. Варианты `--fail-mode`: `error_5xx` (по умолчанию), `bad_request`,
`stopped`. Эмуляция обрыва (`refuse`) не используется по умолчанию намеренно: `ECONNRESET`
классифицируется как `unknown` и по дизайну **не** переключает выбор на B (§2.4) — демо с ним
сообщило бы о провале там, где система ведёт себя штатно.

**Вручную через docker compose** (то же, что `--fail-mode stopped`):

1. `docker compose up -d`, затем `docker compose stop supplier-a` — порт A закрыт, ОС отвечает
   `ECONNREFUSED` на любой `connect()`.
2. Создать заказ на SKU режима `supplier` (`POST /orders`) и оплатить (`POST /webhooks/payment`).
3. Задача `deliver_order` берёт заказ, вызов к A даёт `ECONNREFUSED` → определённый исход
   `unavailable` → выбор сразу переходит к B **в том же claim'е задачи**, без отдельного ретрая.
4. Заказ переходит в `delivered`; в `delivery_attempts` две строки с разными `request_id`:
   `A / attempt_no=1 / failed / connection_refused` и `B / attempt_no=1 / succeeded`.
5. Проверить: `GET /orders/:id` (поля `delivery.supplier` и `delivery_attempts`) или
   `SELECT supplier_code, state, error_kind FROM delivery_attempts da JOIN orders o ON o.id = da.order_id WHERE o.ext_id = $1 ORDER BY da.id;`

Если недоступны оба поставщика — заказ уходит в `delivery_failed`; если оба ответили
`out_of_stock` — в `out_of_stock`. Оба статуса восстановимы (§6.4), а не «падение».

**Автоматически:** `supplier-delivery-fallback.worker.spec.ts` — A стартует на фиксированном
тестовом порту и сразу останавливается, что даёт настоящий `ECONNREFUSED` от ОС (не эмулированный
заглушкой сценарий), и проверяются ровно эти две строки `delivery_attempts` плюс выдача от B.

### 6.3 Ловушка таймаута: поставщик выдал код, но ответ не дошёл (критерий 4)

Заглушка поддерживает сценарий `issue_then_hang`: код резервируется и сохраняется под присланным
`request_id` **до** того, как заглушка зависает и не отдаёт ответ — именно так на практике выглядит
«поставщик выдал код, но ответ потерян».

1. Включить сценарий на A: `POST http://localhost:4001/_control/scenario` с
   `{"mode":"issue_then_hang"}` (примеры curl — §8), затем создать и оплатить заказ на SKU режима
   `supplier`.
2. Клиентский `AbortSignal.timeout` срабатывает раньше, чем A отвечает → исход `unknown`
   (`error_kind: 'timeout'`). Попытка остаётся привязанной к A с тем же `request_id`, переходит в
   `state='unknown'`, задача уходит на переклейм. **Заказ не переключается на B** — исход не
   определённый.
3. На повторном claim'е (после `next_resolve_at`) выполняется повторный `POST /issue` к A **с тем же
   `request_id`**. Заглушка по контракту возвращает ранее зарезервированный код, а не чеканит новый:
   попытка переходит в `succeeded`, заказ — в `delivered`, выдан ровно один код.
4. Проверить `GET /orders/:id`: `request_id` в `delivery_attempts` не изменился между шагами 2 и 3, а
   `issued_deliveries` содержит ровно одну строку — это и доказывает идемпотентный реплей вместо
   повторной выдачи.

Если A не отвечает `SUPPLIER_UNKNOWN_MAX_RESOLVE_ATTEMPTS` раз подряд, попытка помечается
`abandoned_unknown` и выбор уходит к B; сама `abandoned_unknown`-строка остаётся в БД как незакрытый
вопрос (возможен задвоенный код, если A всё же ответит позже) — именно такие расхождения и должен
показывать отчёт сверки, который не реализован (§2.7).

**Автоматически:** `supplier-delivery.worker.spec.ts` (реплей того же `request_id` после реального
сетевого таймаута) и `sweeper-recovery.sweeper.spec.ts` (проходы 5a/5b: демоция зависшего
`in_flight` в `unknown` и редрайв `unknown`-попыток).

### 6.4 Пустой остаток и восстановление (критерий 6)

Три пути восстановления, все поверх одних инвариантов.

**Автоматический (sweeper)** — пополнили остаток, ближайший тик (≤ `SWEEPER_INTERVAL_MS`, по
умолчанию 15 с) сам ретраит заказ:

```bash
# 1. осушить пул: создавать и оплачивать заказы, пока ключи KEY-* не кончатся
#    (для supplier-SKU — обнулить остаток стенда, см. §8)
# 2. заказ уходит в out_of_stock — проверить:
curl -s http://localhost:3000/orders/ord_00123

# 3. пополнить остаток
curl -s -X POST http://localhost:3000/admin/products/KEY-GTA5/restock \
  -H 'x-admin-token: dev-admin-token' -H 'content-type: application/json' \
  -d '{"count":5}'

# 4. дождаться тика sweeper'а (или форсировать его) и убедиться, что заказ доставлен
curl -s -X POST http://localhost:3000/admin/sweeper/run -H 'x-admin-token: dev-admin-token'
curl -s http://localhost:3000/orders/ord_00123
```

**Ручной (admin)** — не ждать расписания:

```bash
curl -s -X POST http://localhost:3000/admin/orders/ord_00123/redeliver \
  -H 'x-admin-token: dev-admin-token' -H 'content-type: application/json' \
  -d '{"reason":"manual retry after restock"}'
```

**Зависшие заказы.** Заказ, застрявший в `paid`/`delivering` дольше `STUCK_ORDER_AGE_SECONDS` без
выдачи и без живой задачи (например, процесс упал между коммитом и постановкой задачи), доводится
проходом 2 sweeper'а; заказ в `delivery_failed` — проходом 4, под потолком
`MAX_DELIVERY_GENERATIONS` (то есть не бесконечно).

Во всех трёх путях защита от задвоения одна: `issued_deliveries_order_uq` и проверка уже
существующей выдачи до постановки задачи; повторный вызов на уже доставленный заказ отвечает
`409 ORDER_ALREADY_DELIVERED`, а устаревшее поколение задачи молча пропускается воркером.

**Автоматически:** `pool-delivery.e2e.spec.ts` (`out_of_stock` при пустом пуле, повтор уже выданного
заказа, пропуск устаревшего поколения), `admin-recovery.e2e.spec.ts` (все три admin-эндпоинта),
`sweeper-recovery.sweeper.spec.ts` (проходы 2/3/4, включая отрицательные кейсы — чего проход трогать
не должен, и конкурентный запуск двух прогонов без задвоения).

### 6.5 Вебхук вне порядка и раньше заказа (критерий 3)

Полностью покрыт `payment-webhook.e2e.spec.ts` (§7.3): `orphan` на неизвестный заказ; `conflict` для
`failed` после `paid`; `rejected_amount` при несовпадении суммы; `ignored_stale` для устаревшего
события; `duplicate` на повтор `event_id`. Вручную любой исход воспроизводится `npm run webhook` —
например, вебхук на ещё не созданный заказ:

```bash
npm run webhook -- --order ord_99999 --status paid --amount 500
```

## 8. Управление стендами поставщиков

Оба стенда (`apps/supplier-stub` под `SUPPLIER_ID=A` и `SUPPLIER_ID=B`) — не «всегда 200 OK», а
управляемый источник хаоса. В режиме `normal` (по умолчанию) на каждый `/issue` бросается кубик по
ставкам `STUB_FAIL_RATE`/`STUB_TIMEOUT_RATE`/`STUB_SLOW_RATE`; через `/_control/scenario` можно
принудительно включить любой из десяти сценариев на N следующих запросов — этим и воспроизводятся
фолбэк A→B и ловушка таймаута (§6.2, §6.3).

| Режим               | Что делает `/issue`                                                                                  |
| ------------------- | ---------------------------------------------------------------------------------------------------- |
| `normal`            | бросает кубик по ставкам (порядок проверки фиксирован: `timeout → error_5xx → slow → ok`)            |
| `ok`                | сразу `200` с кодом                                                                                  |
| `slow`              | `200` после задержки `STUB_LATENCY_MS_MIN..STUB_LATENCY_MS_MAX`                                      |
| `timeout`           | ждёт `STUB_HANG_MS`, ответа не будет никогда                                                         |
| `issue_then_hang`   | код выпускается и сохраняется **до** зависания — ловушка §6.3: код у поставщика есть, ответ не дошёл |
| `error_5xx`         | `500` с `{ "status": "error", "reason": "upstream_unavailable" }`                                    |
| `error_5xx_garbage` | `500` с не-JSON телом (HTML) — проверка, что `apps/api` не падает на разборе                         |
| `out_of_stock`      | `409` с `{ "status": "error", "reason": "out_of_stock" }`, не трогая остаток                         |
| `bad_request`       | `400` с `{ "status": "error", "reason": "sku_unknown" }`                                             |
| `refuse`            | обрыв TCP-соединения без ответа (`ECONNRESET`), не HTTP-ошибка                                       |

При всех трёх ставках `0` результат всегда `ok` — поэтому интеграционные тесты выставляют их в `0` и
включают хаос точечно. Известный `request_id` всегда отдаёт сохранённый код повторно, и это правило
приоритетнее пустого остатка (проверяется отдельным тестом).

```bash
# включить сценарий на 3 следующих вызова /issue (без times — залипает навсегда)
curl -s -X POST http://localhost:4001/_control/scenario \
  -H 'content-type: application/json' -d '{"mode":"error_5xx","times":3}'

# обнулить остаток стенда (следующие /issue дадут out_of_stock)
curl -s -X POST http://localhost:4001/_control/restock \
  -H 'content-type: application/json' -d '{"count":0}'

curl -s -X POST http://localhost:4001/_control/reset  # сбросить сценарий и остаток
curl -s http://localhost:4001/_control/state          # сценарий, остаток, счётчик выданных кодов
```

Состояние (выданные коды, остаток) переживает перезапуск процесса — пишется на диск по
`STUB_PERSIST_PATH` после каждой мутации. Пустое значение переменной отключает персист: стенд
стартует с чистого листа, что и используют тесты.
